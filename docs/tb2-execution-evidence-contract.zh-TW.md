# TB2 Execution Evidence Contract

## Purpose

本文件定義 TB2 對外部 audit orchestration 提供的 execution evidence 合約。

TB2 的責任是執行、傳遞 reviewer 訊息、保留 runtime evidence，並把可驗證的執行證據匯出給外部 orchestrator。TB2 不負責產生 reviewer packet、合併 reviewer 結論，也不宣稱輸出 normalized audit report。

## Ownership Boundary

TB2 owns:

- workstream lifecycle
- reviewer request transport
- reviewer response polling and reading
- process spawn diagnostics
- runtime message evidence
- TB2 audit trail evidence

`external-audit-orchestrator` owns:

- audit packet format
- reviewer request JSON export
- expected reviewer output schema
- reviewer result normalization
- normalized audit report merge
- packet-level fallback workflow

`audit_export` must keep this boundary visible in its output:

```json
{
  "export_type": "tb2_execution_evidence",
  "normalized_audit_report": false,
  "boundary": "TB2 exports execution evidence only; external-audit-orchestrator owns packet schemas and normalized reports."
}
```

## Tool Flow

The minimal TB2-side external audit flow is:

1. `workstream_create`
2. `reviewer_send`
3. `reviewer_wait`
4. `reviewer_read`
5. `audit_export`

The orchestrator may wrap this flow, but it should treat TB2 as a runtime evidence provider rather than a packet/report engine.

## Workstream Resolution

Tools that operate on an existing bridge resolve the target with the shared TB2 bridge resolution inputs:

```json
{
  "workstream_id": "review-main",
  "bridge_id": "bridge-id",
  "room_id": "room-id"
}
```

For the minimal external audit flow, use `workstream_id` from `workstream_create`. `bridge_id` and `room_id` are supported fallback identifiers when the orchestrator only has lower-level TB2 runtime evidence.

## `workstream_create`

Creates a process-backed TB2 workstream and bridge.

Required behavior:

- Default backend is `process` when no backend is supplied.
- `workstream_id` may be supplied by the caller or generated by TB2.
- `session` defaults to `ws-{workstream_id}`.
- Successful startup returns pane ids, backend metadata, and `spawn_diagnostics`.
- If the process starts but bridge creation fails, TB2 must clean up the process session and return `SPAWN_CLEANED_UP`.

Successful output shape:

```json
{
  "workstream_id": "review-main",
  "bridge_id": "bridge-id",
  "room_id": "room-id",
  "session": "ws-review-main",
  "pane_a": "pane-a-id",
  "pane_b": "pane-b-id",
  "backend": {
    "kind": "process",
    "backend_id": "default",
    "shell": "",
    "distro": ""
  },
  "spawn_diagnostics": {
    "code": "SPAWN_OK",
    "category": "process_startup",
    "retryable": false,
    "recommended_action": "",
    "reason": "process session started",
    "detail": "process session started"
  }
}
```

## Spawn Diagnostics

`spawn_diagnostics` is the stable operator-facing process startup diagnostic object.

Required fields:

| Field | Type | Meaning |
| --- | --- | --- |
| `code` | string | Machine-readable diagnostic code |
| `category` | string | Diagnostic class for routing and UI grouping |
| `retryable` | boolean | Whether automatic retry is useful |
| `recommended_action` | string | Operator action when applicable |
| `reason` | string | Short cause derived from the spawn error or cleanup path |
| `detail` | string | Human-readable detail; process spawn failures usually duplicate `reason` for compatibility |

Known diagnostic codes:

| Code | Category | Retryable | Meaning |
| --- | --- | --- | --- |
| `SPAWN_OK` | `process_startup` | false | Process session started |
| `SPAWN_BLOCKED` | `security_intervention` | false | Startup was likely blocked by permission, policy, AV, EDR, Defender, AppLocker, or related security control |
| `SPAWN_FAILED` | `executable_not_found` | false | Target executable is missing or not available on PATH |
| `SPAWN_FAILED` | `temporary_resource_exhaustion` | true | Resource pressure prevented startup |
| `SPAWN_FAILED` | `process_start_failure` | false | Generic startup failure; inspect shell path, cwd, dependencies, and original error |
| `SPAWN_CLEANED_UP` | `bridge_start_failed` | false | Process session started, but bridge creation failed and TB2 cleaned it up |

`SPAWN_BLOCKED` example:

```json
{
  "code": "SPAWN_BLOCKED",
  "category": "security_intervention",
  "retryable": false,
  "recommended_action": "Check antivirus allowlist for node, tb2, target CLI, and runtime directory.",
  "reason": "Access is denied",
  "detail": "Access is denied"
}
```

Operator guidance:

- Do not automatically retry `SPAWN_BLOCKED`.
- Show the allowlist recommendation directly.
- Treat missing executables as setup/config problems, not security intervention.
- Treat generic spawn failures as diagnostics tasks until a stronger signal is available.
- Treat `SPAWN_CLEANED_UP` as an argument or bridge-start validation problem. Fix the `workstream_create` inputs before retrying.

## `reviewer_send`

Sends a reviewer request into the workstream room and optionally delivers it to a bridge pane.

Required input:

```json
{
  "workstream_id": "review-main",
  "text": "review request text"
}
```

Optional input:

```json
{
  "deliver": "b",
  "author": "reviewer_request"
}
```

Output shape:

```json
{
  "id": 1,
  "workstream_id": "review-main",
  "bridge_id": "bridge-id",
  "room_id": "room-id",
  "deliver": "b"
}
```

The posted room message must use:

- `kind`: `review_request`
- default `author`: `reviewer_request`
- default delivery target: `b`

## `reviewer_wait`

Polls the workstream room for messages after a given message id.

Input shape:

```json
{
  "workstream_id": "review-main",
  "after_id": 0,
  "limit": 20,
  "timeout_ms": 30000,
  "poll_ms": 500
}
```

Success output shape:

```json
{
  "workstream_id": "review-main",
  "bridge_id": "bridge-id",
  "room_id": "room-id",
  "messages": [],
  "count": 0,
  "timed_out": true
}
```

`timed_out` is authoritative. An empty message list with `timed_out: true` means the room had no matching messages before the deadline, not that the workstream failed.

`reviewer_wait` does not validate message authors or filter room traffic into normalized reviewer output. It returns the first available TB2 room messages after `after_id`. After `reviewer_send`, an orchestrator should usually set `after_id` to the returned request message `id` so the next wait reads evidence that arrived after the request rather than the request message itself.

## `reviewer_read`

Reads current room messages and captures recent pane output from both sides of the bridge.

The `messages` list is unnormalized room evidence, using the same semantics as `reviewer_wait`.

Input shape:

```json
{
  "workstream_id": "review-main",
  "after_id": 0,
  "limit": 50,
  "lines": 80
}
```

Output shape:

```json
{
  "workstream_id": "review-main",
  "bridge_id": "bridge-id",
  "room_id": "room-id",
  "messages": [],
  "count": 0,
  "capture": {
    "pane_a": {
      "target": "pane-a-id",
      "lines": []
    },
    "pane_b": {
      "target": "pane-b-id",
      "lines": []
    }
  }
}
```

The `capture` block is supporting execution evidence. The orchestrator should not treat captured terminal text as normalized reviewer output unless it has separately parsed and validated that text against its own reviewer schema.

## `audit_export`

Exports TB2 execution evidence for a workstream.

Input shape:

```json
{
  "workstream_id": "review-main",
  "after_id": 0,
  "limit": 100
}
```

Output shape:

```json
{
  "export_type": "tb2_execution_evidence",
  "normalized_audit_report": false,
  "boundary": "TB2 exports execution evidence only; external-audit-orchestrator owns packet schemas and normalized reports.",
  "workstream_id": "review-main",
  "bridge_id": "bridge-id",
  "room_id": "room-id",
  "workstream": {},
  "messages": [],
  "audit_events": [],
  "audit": {}
}
```

Field meanings:

| Field | Type | Meaning |
| --- | --- | --- |
| `export_type` | string | Must be `tb2_execution_evidence` |
| `normalized_audit_report` | boolean | Must be `false` |
| `boundary` | string | Human-readable ownership boundary |
| `workstream_id` | string | TB2 workstream id |
| `bridge_id` | string | TB2 bridge id |
| `room_id` | string | TB2 room id |
| `workstream` | object or null | Current decorated TB2 workstream status |
| `messages` | array | Room messages visible to TB2 |
| `audit_events` | array | TB2 audit trail events for the room and bridge |
| `audit` | object | Audit trail configuration/status summary |

## Message Evidence

Room message objects are TB2 transport evidence.

Expected message semantics:

- `reviewer_send` posts `kind: review_request`.
- Other message kinds may appear because the room can contain operator, client, bridge, or reviewer-side traffic.
- Consumers must preserve message ids when building higher-level audit reports.
- Consumers should use `after_id` to avoid duplicate evidence collection.

## Error Contract

Tool errors return an `error` string.

Examples:

```json
{
  "error": "room not found"
}
```

```json
{
  "error": "workstream spawn failed",
  "workstream_id": "review-main",
  "session": "ws-review-main",
  "spawn_diagnostics": {
    "code": "SPAWN_BLOCKED",
    "category": "security_intervention",
    "retryable": false,
    "recommended_action": "Check antivirus allowlist for node, tb2, target CLI, and runtime directory.",
    "reason": "Access is denied",
    "detail": "Access is denied"
  }
}
```

Callers should branch on `spawn_diagnostics.code` when present. They should not parse `error` strings to classify process startup failures.

## Non-Goals

TB2 does not:

- define the audit packet schema
- export the three reviewer request JSON files
- validate reviewer answers against the orchestrator expected-output schema
- score reviewer outputs
- merge reviewer outputs into a normalized audit report
- decide final audit pass/fail

These responsibilities belong to `external-audit-orchestrator`.

## Compatibility Rules

Future changes should preserve:

- `export_type: "tb2_execution_evidence"`
- `normalized_audit_report: false`
- `spawn_diagnostics.code`
- `spawn_diagnostics.category`
- `spawn_diagnostics.retryable`
- `spawn_diagnostics.recommended_action`
- room message ids
- `after_id` pagination behavior
- the boundary statement that TB2 exports evidence only

If a future version adds fields, consumers should ignore unknown fields unless they explicitly opt into the newer contract.
